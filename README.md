# Skill、工具和 MCP 怎样配合完成任务？

**从“我知道怎么做”，到“有证据证明做完了”**

你让 Agent 测试购物车。它读完 Skill，说要打开页面、点击按钮、检查结果，却没有真正动手。到底缺了什么？

要定位问题，需要拆开方法、调用、执行、连接和验收，跟踪每个环节的输入、状态变化和输出。

**读完后，你应当能做到：**

- 解释 Skill、工具、MCP、宿主与模型各自负责什么。
- 顺着一次调用往返，定位任务停在哪一步。
- 区分操作成功、功能通过、测试完成三种结论。

**阅读范围**

讨论范围是普通工具调用路径，MCP 协议版本为 2026-07-28。购物车、工具名及运行记录使用模拟数据；附带程序验证离线判定逻辑，不连接模型、MCP 服务或真实网站。

## 1. 我们到底要完成什么

### 1.1 先把“测试购物车”变成可判定的目标

假设一个教学商品页有商品 A，购物车中 A 的初始数量为 0。测试要求是：点击一次“加入购物车”，等待页面进入可检查状态，再读取购物车中 A 的数量，最后报告预期值和实际值。

这里暂时排除并发操作、库存不足、登录过期等其他条件。等待方式应依据页面的真实行为设置，不能用“固定等一秒”代替对可检查状态的判断。

| 要素 | 本例约定 |
| --- | --- |
| 初始状态 | 商品 A 的数量为 0 |
| 操作 | 对商品 A 点击一次加入按钮 |
| 功能预期 | A 的数量变为 1 |
| 必需证据 | 商品身份、操作记录、前后数量 |
| 测试交付 | 如实报告通过、发现问题或无法判断 |

### 1.2 三种“成功”不能混用

**操作成功**：执行层报告点击动作已完成。它回答“动作有没有执行”。

**功能通过**：对正确商品的观察满足 0 → 1。它回答“页面行为是否符合预期”。

**测试完成**：完成必要观察并给出有证据的结论。即使数量仍为 0，只要证据完整，也可以交付“发现问题”的测试报告。

相反，如果只有一句“点击成功”，没有读取购物车，测试结论就是证据不足。不能把缺少证据填成“通过”，也不能直接判定页面有缺陷。

### 1.3 讨论范围

我们研究的是“方法怎样接到行动和反馈”。不展开 Skill 发现算法、浏览器定位策略、MCP 初始化流程和生产测试平台搭建。它们可能影响真实系统，但不是解释这条主线所必需的前提。

## 2. 从基本事实推导必要机制

### 2.1 文字描述与外部状态是两件事

Skill 可以保存步骤、参考资料及脚本。读到“点击按钮”提供了行动方法，却没有给浏览器发送动作；脚本作为文件存在，也不代表进程已运行。

以常见客户端工具调用为例，模型输出带名称和参数的请求，应用负责执行相应操作，并把结果回传。也有平台侧执行的工具，因此不应把执行位置限定为用户电脑。

从这两点出发，可以逐层推导缺少什么。

| 原来缺什么 | 最少补什么 | 补上后解决什么 |
| --- | --- | --- |
| 不知道测试步骤和验收标准 | 明确任务方法，如 Skill | 知道怎样组织任务 |
| 无法操作浏览器 | 可调用的浏览器工具 | 有执行具体动作的能力 |
| 没有明确要执行的动作 | 工具名和参数组成的调用请求 | 把意图交给执行层 |
| 请求未被处理 | 宿主路由、检查与执行环境 | 真正尝试改变外部状态 |
| 不知道动作后发生什么 | 结果与再次观察 | 支持下一步决策和验收 |

### 2.2 MCP 解决哪一个额外问题

只有一个应用、几个本地函数时，可以直接接工具。随着多个应用需要接入不同能力，工具描述、请求和结果的对接方式容易各不相同。MCP 为兼容的客户端与服务端提供共同的交换约定。

因此，MCP 是连接能力的一种方式；它不凭空生成浏览器实现，也不负责保证测试方法正确。移除 MCP、改用直接适配器，任务仍可能完成；移除执行能力，只有方法说明就不能点击页面。

### 2.3 关键定义

**Skill 是方法包，工具是可调用的操作，模型提出下一步，宿主组织执行和反馈，MCP 可以承担其中的连接。**

这是一种便于理解的职责划分，不要求所有产品内部恰好有五个独立模块。真实系统可能把多个职责放在同一进程，也可能拆到远端服务。

## 3. 跟着一个最小例子推演

### 3.1 从输入到结果

继续使用商品 A，初始数量为 0。本例假设工具已经接入、页面已打开、定位信息有效，且本次操作获准执行。这样能把注意力放在调用与验收的区别上。

| 步骤 | 输入或已有信息 | 发生了什么 | 新增证据 |
| --- | --- | --- | --- |
| 1 | 测试要求与商品 A | 读取当前数量 | A 的数量为 0 |
| 2 | Skill 方法与工具定义 | 模型提出点击请求 | 名称、参数和调用标识 |
| 3 | 点击请求 | 执行层检查并点击 | 本次操作结果 |
| 4 | 点击后的页面 | 等待并再次读取 | A 的实际数量 |
| 5 | 前后观察与预期值 | 比较并生成报告 | 功能结论及其依据 |

### 3.2 用数值固定判断条件

设初始数量为 q₀，预期增加量为 1，则 q_expected = q₀ + 1。我们的输入是 q₀ = 0，所以预期数量为 1。

功能通过至少要求：观察对象仍是商品 A，观察有效，且 q_after = q_expected。本例还要求有一次成功操作的记录，因为测试目标包含一次实际点击。

**情况一：点击成功，A 的数量为 1。** 证据满足本例条件，可以报告通过。

**情况二：点击成功，A 的数量仍为 0。** 完成必要等待与有效观察后，可报告本次功能检查不通过；原因仍需继续定位，不能单凭数量就断言是哪段代码有错。

**情况三：点击成功，只读到了商品 B 的数量为 1。** 数值看似正确，但观察对象错误，应报告证据不足。

### 3.3 拿掉一项，看看结论是否仍成立

拿掉观察，无法知道实际结果；拿掉商品身份，可能把别的商品当成目标；拿掉执行记录，则无法证明按要求做过这次点击。

这就是本例需要“方法、行动、观察、判定”四部分的原因。它是对任务成功条件的推导，不是靠工具名称推断完成。

## 4. 整体架构：谁负责什么

![图4-1 方法进入上下文，操作进入执行层](assets/architecture.png)

**图4-1｜工具执行架构。** 宿主选取方法、工具定义与已有结果交给模型；模型返回调用请求。宿主可以直接路由到本地适配器，也可以经 MCP 客户端连接服务端。两条执行路径是可选接入方式，不要求每次同时走两条。

| 角色 | 本例职责 | 不能据此推断 |
| --- | --- | --- |
| Skill | 给出步骤、缺输入处理、验收标准 | 读完就执行过了 |
| 模型 | 根据当前上下文提出调用或回答 | 生成请求就改变了页面 |
| 宿主 | 提供上下文、路由、检查、回传结果 | 仅连通就具有全部权限 |
| 工具执行层 | 按参数执行操作并返回结果 | 点击完成就代表功能通过 |
| MCP 客户端与服务端 | 按协议交换能力、调用及结果 | 协议替你安排完整测试 |

MCP 客户端由宿主管理，服务端是提供能力的程序角色，可以运行在本地或远端。 图中的执行环境表示逻辑边界，不规定网络或进程的实际部署位置。

## 5. 一次调用怎样往返

![图5-1 经MCP执行点击并继续观察的调用时序](assets/sequence.png)

**图5-1｜工具已接入后的成功主路径。** “提供上下文”包含方法与可用工具说明。图中省略发现、鉴权握手和传输细节，聚焦调用后的因果顺序；具体产品可能拆分或合并部分操作。

### 5.1 先发现能力，再处理调用

MCP 工具路径使用 tools/list 获取工具说明，使用 tools/call 调用操作。 宿主决定怎样向模型提供这些能力；Skill 的方法选择和可执行工具的发现不是同一件事。

### 5.2 在哪里检查权限

宿主可以在路由前限制操作；服务端及后端业务也可能按当前身份拒绝请求。具体检查位置依实现而定，Skill 里的文字不会自动改变这些限制。

### 5.3 如果某一步失败

模型没发请求，应先检查指令、工具定义和调用配置。宿主已拒绝时，本次请求不应继续走向执行成功；服务端执行报错时，需要把失败反馈回去，再按策略补信息、停止或重试。重试不是任何错误的默认答案。

## 6. 数据、契约与证据关系

### 6.1 先区分三份信息

**方法说明**回答“怎样完成测试”。例如：读初始数量、点击一次、等待并读取最终数量、按证据报告。

**工具定义**回答“这个操作怎样调用”。本例定义示例工具 browser_click，参数是 page_id 和 target_ref；实际工具名称和参数以接入实现为准。真实工具定义需说明用途与输入结构。

**调用实例**回答“这一次究竟要求做什么”。下面采用简化的调用表示，省略了模型 API 或 MCP 协议要求的完整报文字段，不能直接发送。

```json
{
  "call_id": "C1",
  "tool_name": "browser_click",
  "arguments": {
    "page_id": "P1",
    "target_ref": "add-product-a"
  }
}
```

### 6.2 为什么结果需要关联到这一次调用

如果同一任务先打开页面再点击按钮，不能把“页面打开成功”的结果当成“点击成功”。调用标识帮助关联请求和对应结果；它与任务标识、商品标识承担不同职责。

| 本例字段 | 含义 | 主要作用 |
| --- | --- | --- |
| task_id | 一次测试任务 | 汇总相关操作与观察 |
| call_id | 一次操作请求 | 避免混用不同调用结果 |
| product_id | 被检查的商品 | 确认观察对象正确 |
| quantity | 某次观察得到的数量 | 对照期望值 |
| observed | 是否获得有效观察 | 区分零与没有读到数据 |

“没有读到数量”不等于“数量为0”。工具执行反馈与页面观察也应分别记录，才有可能在报告中说明卡住的位置。

### 6.3 用一张逻辑ER图组织证据

![图6-1 测试任务与证据的逻辑实体关系](assets/evidence-er.png)

**图6-1｜测试任务与证据的逻辑实体关系。** 一项任务关联零到多条调用记录和零到多条观察记录；每条记录只属于一个任务。“零到多”保留了尚未调用或未取得观察的失败情况。这是本例的逻辑数据模型；MCP不规定这些实体，也不要求按此模型建表。

- TASK 保存目标与期望；CALL 保存操作输入和执行结果；OBSERVATION 保存目标身份、数量与观察阶段。
- OBSERVATION 使用 before / after 区分操作前后；真实系统还可记录观察时间、页面状态和证据位置。
- 此处的标识是逻辑键，不声明数据库外键、存储方式或持久化能力。关系用于解释证据如何归属。

### 6.4 两个维度分别记录

**执行维度**：没有调用、被拒绝、执行失败、执行成功。

**验收维度**：尚未判断、证据不足、功能通过、功能不通过。

它们不能挤进一个含义模糊的 success 字段。执行成功可以对应功能不通过；证据不足也不能冒充功能不通过。本例附件采用简化字典记录这些信息，不实现数据库或MCP消息存储。

## 7. 自己验证一次

### 7.1 离线练习的目标与运行方法

附件 examples/evaluate_trace.py 使用 Python 3 标准库，不需要 API Key、模型服务、浏览器或额外依赖。它输入六份固定的模拟记录，输出执行与验收结论，帮助检验第3章的判断条件。

在文档所在目录运行：

```text
python3 examples/evaluate_trace.py
```

运行输出见 [运行结果](examples/运行结果.txt)。程序核对判定逻辑与预设用例是否一致，不执行浏览器点击、页面等待或模型工具选择。

### 7.2 六种情形，应当怎样判断

| 模拟输入 | 预期结论 | 原因 |
| --- | --- | --- |
| 没有调用 | 未执行 | 只有意图，没有操作请求 |
| 请求被拒绝 | 执行受阻 | 当前请求没有获准执行 |
| 点击成功，无后续观察 | 证据不足 | 无法核对目标状态 |
| 点击成功，A仍为0 | 功能未通过 | 有效观察不满足预期 |
| 点击成功，A变为1 | 功能通过 | 满足本例全部条件 |
| 点击成功，读到B为1 | 证据不足 | 观察对象不是商品A |

### 7.3 运行结果与验证范围

六个预设用例均得到表中的预期结论，程序正常退出。此结果仅覆盖这些输入；不证明该判定逻辑适用于所有网页测试，也不构成对真实系统性能或可靠性的评估。

你可以把初始数量改为2，再将期望数量设为3，检查推理是否仍成立。也可以删掉 observed，观察为什么程序不能把缺失证据判成通过。

## 8. 取舍、失败与适用边界

### 8.1 什么时候需要MCP

已经直接接好的少量工具，可以继续走现有适配器。需要跨兼容应用复用服务能力时，可以考虑 MCP，但仍要维护工具实现、权限、版本兼容和运行环境。统一连接约定并不意味着接入成本为零。

Skill 则适合沉淀反复使用的操作方法和验收规则。对于一次简单任务，清晰指令可能已足够；方法复杂、需重复使用时，方法包的组织价值更明显。实际收益应在相同任务与环境下比较，不能仅靠安装数量判断。

### 8.2 按证据定位，而不是重写所有提示词

| 观察到的现象 | 优先检查 | 不宜直接下的结论 |
| --- | --- | --- |
| 只复述操作步骤 | 有无可调用工具及真实调用请求 | Skill必然写错 |
| 工具列表里有，调用却失败 | 参数、宿主策略、服务端权限 | 连接成功就能执行 |
| 超时，不知道是否已点击 | 执行记录与页面实际状态 | 没收到返回就是没执行 |
| 点击完成，商品未增加 | 等待条件、正确商品、实际观察 | 一定是浏览器工具故障 |
| 报告通过却没有观察证据 | 验收标准与证据链 | 模型说完成就已完成 |

### 8.3 为什么不能一律重试

如果请求超时，但点击已经生效，再点一次可能把数量从1变成2。本例并未实现幂等控制；真实系统应根据操作副作用、可查询状态及具体策略处理。权限拒绝也不应该靠重复提交绕过。

MCP中的协议错误与工具执行错误有不同表示。 但错误表示只提供事实，恢复方式仍依赖任务和实现。真实测试还要确认截图、页面数据的有效性，以及观察时点与对象是否正确。

## 9. 换个场景，检验理解

### 题一：目录里放了脚本，为什么没有效果

Skill 随包提供 test_cart.py，并写了“运行脚本测试购物车”。Agent 读完文件后输出了测试步骤，磁盘上没有报告。最先需要检查什么？

**参考答案：** 先检查有无可调用的命令工具、是否真正发出执行请求。若已发出，再看依赖、权限、执行结果与报告路径。脚本存在只是方法包提供了资源，不能证明它已经运行。

### 题二：点击超时，应不应该立即再点

调用超时，没有拿到结果。随后观察到商品 A 数量从0变成1。能否直接再次点击以“确保成功”？

**参考答案：** 不应立即重复有副作用的动作。先核对本次调用及当前状态，判断是否已经满足目标。此时至少有“操作可能生效”的证据；第二次点击可能改变测试输入。能否确认由本次调用导致，仍取决于是否排除了并发等因素。

### 题三：换成导出文件，应该验收什么

把任务换成“将三条记录导出为CSV”。工具返回“文件写入成功”，是否足够报告任务完成？

**参考答案：** 还要核对文件位置、记录数量、字段、内容与编码等任务约定。写入成功对应操作层；正确导出对应任务目标。如果导出的是错误记录，执行可能成功，任务却不满足要求。

### 为什么这三题能检验理解

三题分别改变执行资源、返回状态与任务类型。真正可迁移的知识是：先找任务目标，再核对调用、执行、观察和验收之间的联系。记住产品名称无法代替这条推理路径。

## 10. 一页复习

### 10.1 记住这条因果链

**有任务目标 → 需要方法 → 需要可执行能力 → 发出具体调用 → 在边界内执行 → 获得结果与观察 → 对照目标判定。**

MCP可以连接其中的工具能力，Skill可以提供任务方法和验收要求。宿主把模型提出的调用接到执行环境，再把证据送回后续决策。

### 10.2 遇到“装了却没用”，检查五件事

1. **方法是否读到？** 本次上下文是否包含适用步骤和验收条件。
2. **能力是否可用？** 所需工具、依赖和环境是否具备。
3. **调用是否发出？** 是自然语言计划，还是可执行的结构化请求。
4. **执行是否发生？** 是否被拒绝、报错、超时，返回结果对应哪次调用。
5. **目标是否核对？** 观察对象与预期是否一致，报告有没有证据。

这五项是一种排查顺序，并非所有 Agent 的固定内部实现。

### 10.3 三句话带走

**方法不会自行执行。** 读到Skill、看到脚本，都不能替代调用和执行记录。

**连接不等于授权。** 客户端与服务端能够通信，不代表当前请求获准做所有操作。

**执行不等于验收。** 工具成功返回之后，仍要检查实际目标；发现问题也可以是一次完成的测试。
